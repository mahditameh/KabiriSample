# راهنمای استفاده از پرامپت‌های بازآرایی

این فایل‌ها راهنمای کدنویسی‌اند و به پروژه مشخصی وابسته نیستند. نام فایل‌های موجود برای حفظ ارجاع‌ها تغییر نکرده است.

| فایل | کاربرد |
| --- | --- |
| RefactoringPrompt.md | خوانایی، سادگی، حذف تکرار و بررسی‌های تخصصی .NET/EF/LINQ در صورت ارتباط |
| CommentLoggingPrompt.md | بازبینی و اصلاح کامنت‌ها، لاگ‌ها، مالک ثبت خطا و محرمانگی |
| TestPrompt.md | انتخاب تست بر اساس ریسک و تضمین واقعی ابزارها |
| UIRefactorinPrompt.md | بازآرایی UI در پروژه‌های Blazor با توجه به مدل میزبانی |
| event-driven-design.md | تحلیل و بهبود طراحی رویدادمحور بدون فرض زیرساخت خاص |

## نحوه استفاده

فایل مرتبط را همراه محدوده درخواست و کد یا دسترسی به repository بده. برای کامنت و لاگ، CommentLoggingPrompt.md پرامپت اصلی است. پرامپت‌های دیگر خلاصه قواعد آن را هم دارند تا در استفاده مستقل قابل اجرا باشند.

اطلاعات ورودی مفید:
- محدوده فایل‌ها یا قابلیت و هدف تغییر.
- تحلیل صرف یا اجازه ویرایش کد.
- حفظ قراردادها و محدودیت‌های سازگاری.
- دستور build/test در صورت مشخص بودن.
- سیاست موجود برای audit، داده حساس و لاگ، در صورت وجود.

ابزار، نسخه، معماری و الگوی پروژه را از شواهد واقعی استخراج کن. نمونه‌های .NET الزام برای پروژه‌ای با زبان دیگر نیستند. دستور صریح کاربر و الزامات واقعی پروژه بر ترجیح عمومی این متن‌ها مقدم‌اند.

## متن آماده برای شروع

> کد محدوده مشخص‌شده را مطابق پرامپت کامنت‌گذاری و لاگ‌نویسی بازبینی و اصلاح کن. پیش از افزودن لاگ، پوشش مدیریت خطای مرکزی و tracing/audit را بررسی کن. کامنت‌های بدیهی، قدیمی و تکراری را حذف یا اصلاح کن و توضیحات لازم درباره چرایی و قراردادهای غیرآشکار را حفظ کن. شکست‌های مهم فاقد پوشش را در مرز مسئول با سطح مناسب، template ثابت، exception اصلی و context حداقلی ثبت کن. از ثبت تکراری، لاگ پرتعداد و افشای داده حساس جلوگیری کن. رفتار و قراردادهای برنامه را حفظ کن و تغییرات، شواهد، نتیجه بررسی‌های متناسب و محدودیت‌ها را گزارش بده.

## معیار بازبینی خود پرامپت‌ها

- نام پروژه، entity، provider یا کتابخانه اختصاصی را بدون ورودی فرض نکنند.
- قواعد متناقض یا الزام‌های مکانیکی مانند کامنت برای هر متد و لاگ برای هر عملیات نداشته باشند.
- الزام فنی و ترجیح سبکی را تفکیک کنند.
- دامنه بررسی، مالک خطا و معیار پذیرش روشن باشد.
- هیچ ادعای اجرا، امنیت یا تضمین تحویل را بدون شواهد مطالبه نکنند.
